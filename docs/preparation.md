## OpenSpec 实际采用方式

已阅读全局包 README、CLI 帮助与初始化生成的 `openspec-explore` / `openspec-propose` 技能说明。用户已授权项目初始化和规划文件。

实际执行并成功：

```powershell
openspec.cmd --version
openspec.cmd schemas --json
openspec.cmd init --tools codex --profile core --language zh --no-animation
openspec.cmd list --json
openspec.cmd list --specs --json
openspec.cmd context --json
openspec.cmd doctor --json
```

初始化生成 `openspec/config.yaml` 与 `.agents/skills/` 下六项技能：explore、propose、apply-change、update-change、sync-specs、archive-change。`doctor` 返回 `healthy: true`；changes/specs 列表为空。无全局配置更改。初始化及后续检查用进程环境变量 `OPENSPEC_TELEMETRY=0`，没有写系统环境变量。

当前使用探索方式整理已有授权范围的说明，等待后续口述和运行端选择。模型已确认是 PMX 2.0，具备骨骼和表情；实际渲染仍待验证。正式变更采用以下流程，名称只是示例：

1. 从明确的首版范围创建 change：`openspec.cmd new change <name>`，不手工创建 change 元数据。
2. 读取 `status --change <name> --json`，再依次调用 `instructions proposal/specs/design/tasks --change <name> --json`；根据依赖与返回模板写 proposal、行为规格、设计和任务。记录待决定事项，避免把候选引擎写成已确认要求。
3. `openspec.cmd validate <name> --strict --no-interactive` 检查规格结构；行为场景另行实际核验。Codex 可用 `$openspec-propose` 完成规划、`$openspec-apply-change` 实施。
4. 实施时保留验收证据和未完成任务；若需求改变，先更新规格与设计，再继续实现。
5. 完成行为验收后通过 `$openspec-archive-change` 或 `openspec.cmd archive <name>` 归档并更新主规格；归档前核对任务与实际结果，不以文件存在或 CLI 状态替代测试。

没有创建空的产品 change，也没有执行 apply 或 archive。核心 profile 没有独立 verify 技能；仍可执行实际测试并记录结果，不必更改全局 profile。

## 候选架构与选择依据

建议先分离角色核心与表现适配层，避免资产格式尚未确定时绑定引擎。可实施的接口边界：输入 → 会话编排 → 角色设定/记忆检索 → 模型响应 → 语音与动作调度 → 渲染/音频输出；共同经历另经提取、校验和持久化回写。

| 选择 | 适用条件 | 首步验证 |
| --- | --- | --- |
| 改造 D_sakiko | 用户接受桌面方向，资产和动作需求适配其现有机制 | 核验实际版本、代码边界和许可，评估替换角色及记忆机制的成本 |
| 独立核心 + Live2D 适配 | 到位资产为有效 Live2D 包 | 加载模型、参数、动作和表情，核实口型控制 |
| 独立核心 + 3D 适配 | 到位资产为 VRM / glTF / FBX / PMX 等 | 核实骨骼、表情、动作和目标运行时兼容性，再选引擎 |

上述均为候选。运行端可以是桌面、网页或游戏 NPC；不预选其中任何一项。存储可先评估本地事件日志与结构化数据库，向量检索作为派生索引，避免把唯一记忆放在不可审计的摘要或向量中。具体语言、数据库、ASR/LLM/TTS 服务和训练框架待决定。

参考仓库当前 [README](https://github.com/MacchaPafe/D_sakiko) 描述 ASR、LLM、GPT-SoVITS、Live2D 链路，同时已声明长期记忆与异步反思。因此不能把它概括为只有静态剧情检索，也不能仅凭 README 认定稳定成长已验证。本轮未克隆或运行其代码；先前代码分析中的检索预算和世界书筛选是历史参考，需固定版本后复核。

## 记忆与角色成长的候选约束

原作事实、用户陈述、共同经历和角色主观解释分开记录；模型生成的猜测不能直接成为已发生事实。记忆候选保留事件 ID、会话与时间、参与者、来源片段、角色知情范围、世界分支、修订关系。角色内心变化是带证据的解释，不覆盖原作事实。

先保存事件证据，再抽取和校验；保留原始来源以便检索回溯。中断恢复使用稳定 ID 防止重复写入；有冲突时保留冲突并澄清，不静默覆盖。需要评估查看、纠正、删除和重建检索索引的能力。关系变化不以单一好感度替代，成长边界由用户决定。

## 候选最小里程碑与验收行为

| 里程碑 | 交付范围 | 候选可验收行为 |
| --- | --- | --- |
| M0 需求与资产确认 | 清点文件、格式/许可/绑定报告、首版规格与设计任务 | 能说明真实可用资产、渲染约束、语音来源和首版范围；待定项不伪装成决定 |
| M1 角色表现切片 | 实际模型加载、最小动作调度、真实音频播放 | 模型能执行资产支持的待机和至少一个明确触发动作；发声能听见，动作/表情/口型控制能与播放事件协调，打断或播放失败后恢复合理状态。资产若缺绑定/动作，先报告修补需求 |
| M2 共同经历闭环 | 对话事件保存、检索、跨会话回忆与角色行为适配 | 会话 A 约定一个具体共同经历，重启后 B 能准确引用；对未发生经历承认未知；纠正后的说法用于后续互动；角色表现同时输出语音与动作。用固定脚本保存事件记录和观察证据 |
| M3 声音训练闭环 | 获授权数据导入、切分/转写校验、训练任务、评估与模型版本切换 | 用户确认素材来源后才训练；记录数据清单和训练配置，能够试听固定文本、检查可懂度和目标风格、失败恢复、切回旧模型。时延/质量阈值依设备与首版目标再定 |

文本或模拟服务可以用于调试接口，但不能作为满足角色产品目标的最终验收。M1/M2 是否合并为第一版、是否先用已有获授权声音、何时启用 ASR，均待后续需求。声音训练和日常 TTS 推理是不同工作流。
